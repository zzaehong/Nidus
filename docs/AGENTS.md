# Nidus 작업 지침

Nidus 저장소에서 작업하기 전에 반드시 [Git Flow 문서](Git_Flow.md)를 읽고 그 규칙을 따른다. 이 문서는 브랜치 생성, 커밋, 테스트, 병합, 원격 반영의 기준 문서다.

## 기본 원칙

- 최신 `develop`에서 `feature/<name>` 브랜치를 만든 뒤 작업한다.
- 변경사항은 검증 가능한 논리 단위로 나누어 커밋한다.
- 커밋 메시지는 한글 접두어(`기능:`, `수정:`, `테스트:`, `문서:`, `정리:` 등)를 사용한다.
- 관련 테스트를 실행하고 결과를 실제 상태 그대로 기록한다. 실행하지 못한 테스트는 `NOT RUN`으로 남긴다.
- 관련 변경을 하나의 완결된 feature 작업으로 모아 논리 단위로 커밋한다. 개별 커밋이나 작은 수정 직후에 `develop`으로 병합하지 않는다.
- feature 범위를 구현·검증한 뒤 변경 요약, 커밋, 테스트 결과를 보고하고 사용자의 **명시적인 develop 병합 승인**을 기다린다. 승인 전에는 feature 브랜치에만 둔다.
- 승인된 feature만 `develop`에 `--no-ff`로 병합하고, 병합 후 회귀 테스트를 실행한다. 승인 이후 feature 내용이 바뀌면 다시 승인을 받는다.
- 사용자가 직접 수정한 파일, 기존 기록, 검증 evidence는 임의로 삭제하거나 되돌리지 않는다.
- `main`, `release/*`, `hotfix/*`, 원격 저장소, 강제 push는 사용자가 명시적으로 요청한 경우에만 변경한다.
- 비밀키, 런타임 데이터베이스, 임시 파일을 저장소에 커밋하지 않는다.

## 작업 시작 점검

```bash
git status
git branch --show-current
git fetch
git switch develop
git pull --ff-only
git log -1 --oneline
```

미커밋 변경사항이 있으면 먼저 상태를 확인하고 보존한다. `reset --hard`, 강제 복원, `stash drop`, history rewrite로 사용자 변경을 제거하지 않는다.

## 완료 보고

최종 보고에는 시작과 종료 시점의 `develop` HEAD, 사용한 feature 브랜치, 주요 커밋, 실행한 테스트 결과(`PASS`/`FAIL`/`NOT RUN`), 병합 승인 대기 여부, `main` 변경 여부, 원격 반영 여부, 작업 트리 상태를 포함한다.


## Ponytail 기반 개발 원칙

출처: Ponytail 공식 [AGENTS.md](https://github.com/DietrichGebert/ponytail/blob/main/AGENTS.md), [SKILL.md](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md) (2026-10-30 확인). 아래는 핵심 원칙을 Nidus에 맞게 요약한 것이며, 스킬 설치·세션 모드·Hook을 도입하지 않는다.

- **최소의 완결된 변경:** 요청한 문제를 모두 해결하는 가장 작은 구현을 선택한다. 요청하지 않은 기능·옵션·미래 확장 코드는 추가하지 않는다. 변경량을 줄이려고 필요한 작업을 누락하지 않는다.
- **먼저 영향 범위 확인:** 관련 코드와 모든 호출부, 테스트·fixture·설정·export를 확인하고 호환성, 데이터 손실·노출 위험을 살핀다. 버그는 가능하면 공통 경로의 근본 원인을 한 번 수정한다.
- **재사용 우선:** 기존 프로젝트의 helper·컴포넌트·패턴 → 표준 라이브러리·플랫폼 기능 → 이미 설치된 의존성 → 필요한 최소 새 코드 순으로 검토한다. 기존 계층·인터페이스·관례를 유지한다.
- **추상화와 의존성 절제:** 목적 없는 wrapper·변환·설정·보일러플레이트를 만들지 않는다. 단순한 기능을 위해 새 의존성을 추가하지 않으며, 추가가 필요하면 기존 수단으로 해결하기 어려운 이유를 설명한다. 불필요한 코드는 작업 범위 안에서만 제거하고 사용자 데이터·검증 기록은 보존한다.
- **읽기 쉬운 구현:** 줄 수보다 이해하기 쉬운 코드를 우선한다. 주석에는 코드만으로 드러나지 않는 이유를 적고, 제한된 구현에는 한계와 개선이 필요한 조건을 남긴다.
- **필수 품질 유지:** 보안·신뢰 경계 검증·예외 처리·데이터 무결성·접근성·사용자 요구사항을 단순화 명목으로 줄이지 않는다. 코드 이동·통합 시 기존 검증과 오류 처리를 보존하고, 비슷한 규모라면 경계 조건에 올바른 구현을 택한다.
- **검증까지 완료:** 새 분기·반복·파서·금액·보안 등 의미 있는 로직에는 위험에 맞는 테스트를 추가하고 영향받는 호출부·fixture도 갱신한다. 사소한 변경에 형식적인 테스트를 만들 필요는 없지만 기존 필수 검사·회귀 테스트를 면제하지 않는다.
- **간결한 보고:** 변경 결과와 함께 생략·미검증 사항 및 사용자가 알아야 할 한계를 짧게 알린다. 기존 완료 보고 항목은 유지한다.

이 원칙은 위 프로젝트 지침과 Git Flow를 보완한다. Ponytail의 짧은 보고·테스트 최소화·삭제 우선 원칙을 기존 승인 절차, 필수 검증 또는 기록 보호를 생략하는 근거로 사용하지 않는다. 실제 충돌이 생기면 기존 지침을 임의로 바꾸지 말고 충돌 내용과 대안을 보고한다.
