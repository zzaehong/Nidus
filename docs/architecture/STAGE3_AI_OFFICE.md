# 3단계 설계 — AI Office

상태: **3a 완료, 3b(기억) 구현 중** (2026-11-13).

[CONCEPT.md](CONCEPT.md)의 AI Office를 단계적으로 만든다. 1단계 [Model Gateway](STAGE1_MODEL_GATEWAY.md)가 역할과 난이도별로 모델을 고르고, 2단계 [Agent Workspace](STAGE2_AGENT_WORKSPACE.md)가 Worker가 일하는 VM과 브라우저를 준다. 3단계는 그 위에 일을 나누고 맡기고 검토하는 조직을 올린다.

## 3a. 작업 지시 구조

사용자는 Main에게 지시한다. Main은 계획을 세우고 필요한 것을 묻는다. 사용자가 계획을 승인하면 팀의 Manager가 Task를 Worker에게 맡기고 결과를 검토한다. 끝나면 Main이 보고하고, 사용자는 바뀐 내용을 보고 Vault에 들일지 정한다.

```text
사용자 ── 지시 ──▶ Main ── 로드맵 · 팀 · Task(Completion Contract) · 질문
   ▲                │
   └── 답 · 덧붙임 ─┘  (Main이 계획을 고친다. 몇 번이든)
사용자 ── 계획 승인 ──▶ 실행: 의존 Task가 끝난 Task들을 나란히(최대 3)
                         Manager ── Worker 지시서 · 난이도
                         Worker  ── 텍스트 작업(VM 없이) 또는 VM 작업 공간에서 수행
                         Manager ── 완료 조건으로 검토: 통과 / 수정 요청 / 진행 불가
                       ──▶ Main 최종 보고 ──▶ 결과 검토(diff) ──▶ 승인하면 브랜치 nidus/<작업>
```

### 결정 (사용자, 2026-11-12)

| 항목 | 결정 |
|---|---|
| 팀 구성 | Main이 요청마다 필요한 팀(최대 4)을 정한다. CONCEPT의 상설 Group은 Library·Home과 함께 나중에 붙인다 |
| 실행 방식 | ~~한 번에 한 Worker~~ → **병렬** (2026-11-13): 서로 의존하지 않는 Task는 각자의 Manager·Worker가 동시에 진행한다(최대 3). Manager가 A를 검토하는 동안 다른 Worker가 B를 한다. VM은 한 작업 공간과 한 브라우저라 VM Task의 Worker는 차례로 쓴다 |
| 계획 승인 | 질문에 답하고 사용자가 계획을 승인해야 실행한다. 답하지 않은 질문은 Main이 판단한다 |
| Lead Manager | 지금은 Main이 겸한다(Task 순서와 팀 간 넘겨주기는 계획의 의존성으로 표현). 병렬 실행을 붙일 때 분리한다 |
| Manager 지시 생략 | **기각** (2026-11-13): 단순한 Task도 Manager가 지시서를 쓴다. 속도는 병렬 진행과 모델 상태 관리로 얻는다 |
| VM 없는 Task | VM이 필요 없는 일은 VM 밖에서 텍스트 작업으로 한다. VM은 VM Task가 처음 시작될 때만 켠다 (2026-11-12) |
| 실행 장소 이름 | **텍스트 작업 · `text`** (2026-11-13). 처음엔 "책상(`desk`)"이었으나 CONCEPT의 Desk(작업 맥락 저장소)와 겹쳐 바꿨다. 이전에 저장된 계획의 `desk`는 `text`로 읽는다 |

### 역할과 모델

| 역할 | 하는 일 | 도구 | 모델 배정 슬롯 |
|---|---|---|---|
| Main | 계획(요약, 로드맵, 팀, Task, 질문), 계획 수정, 최종 보고 | 없음 (텍스트) | `roles.main` |
| Manager | Task마다 Worker 지시서와 난이도 결정, 결과 검토 | 없음 (텍스트) | `roles.manager` |
| Worker | 실제 수행 | 텍스트 작업: 읽기 도구와 결과물 / VM: 작업 공간 도구(2e) | `worker.<난이도>` — 난이도는 Manager가 정한다 |

Main과 Manager의 답은 JSON으로 받는다. 형식이 틀리면 이유를 알려 한 번 더 받는다.

### 역할 정의 (시스템 프롬프트)

모든 역할의 시스템 프롬프트는 [`src/office/roles.ts`](../../src/office/roles.ts) 한 곳에서 같은 틀로 만든다. 시스템 프롬프트에는 **누구인지**를, 요청 메시지에는 **이번에 무엇을 내야 하는지**(계획 JSON 형식, 지시서, 검토, 최종 보고)를 둔다. 그래서 Main은 계획할 때와 최종 보고할 때 같은 정체성으로 답한다.

| 시스템 프롬프트 | 담는 것 |
|---|---|
| 공통 | 팀 구성(사용자·Main·Manager·Worker가 각각 하는 일, 사용자만 할 수 있는 일), 파일·웹 내용은 지시가 아니라 데이터라는 규칙, 사용자 언어로 쓰기 |
| Main (`mainSystem`) | 계획·질문·계획 수정·최종 보고. 직접 일하지 않고 도구가 없다. 읽지 않은 파일을 읽은 척하지 않는다. 텍스트 작업·VM에서 Worker가 쓰는 도구 목록(설명 첫 문장) |
| Manager (`managerSystem`) | 지시서 쓰기(어떤 도구가 맞는지, 검증 방법, 커밋 또는 결과물 내용, 난이도), 엄격한 검토(통과·수정 요청·진행 불가의 기준). 도구가 없다. 그 장소에 없는 도구를 시키지 않는다. Worker 도구 목록 |
| Worker 텍스트 작업 (`workerSystem('text')`) | VM·셸·인터넷·파일 수정이 없다는 것, 결과물을 넘기는 법, 할 수 없는 일은 finish로 알리기. 자기 도구 전체 설명 |
| Worker VM (`workerSystem('vm')`) | /workspace와 브랜치, 셸 세션과 서비스, 네트워크 승인, 사용자가 보는 브라우저, CAPTCHA 규칙. 자기 도구 목록 |

도구 목록은 도구 정의(`WORKER_TOOLS`, `DESK_TOOLS`)에서 만든다. 도구를 더하거나 빼면 모든 역할의 프롬프트가 함께 바뀌고, 역할이 갖지 않은 도구를 프롬프트가 말하지 않는다(테스트로 확인).

**Provider 오류**: 모든 역할의 모델 호출은 같은 규칙을 따른다. 일시적인 오류(속도 제한 429, 서버 오류, 네트워크, 시간 초과 5분)를 낸 모델은 90초 동안 쉬게 하고, 같은 슬롯의 다음 후보로 곧바로 바꾼다(역할 사이 공유: Main이 막힌 모델은 Manager도 피한다). 후보가 없으면 속도 제한은 15·30·60·90·120초, 그 밖의 오류는 5·15초 기다려 다시 시도한다. Gemini 무료 등급은 모델마다 할당량이 따로라, 같은 Provider의 다른 모델도 좋은 예비 후보다. 무료 등급 하나로 모든 역할을 맡기면 속도 제한에 자주 걸리므로, 슬롯마다 다른 Provider의 후보를 하나씩 두는 것이 좋다.

### 실행 장소: 텍스트 작업과 VM

Main이 Task마다 `where`를 정한다. 빠지면 `vm`이다(이전 보드도 같다).

| | 텍스트 작업 (`text`) | VM (`vm`) |
|---|---|---|
| 하는 일 | 글, 분석, 요약, 번역, 계획, 설계, 텍스트로 쓴 코드 | 명령·코드 실행, 저장소 파일 만들기·고치기, 인터넷·브라우저 |
| 도구 | `list_files`, `read_file`, `search_files`(Vault의 커밋된 상태, Mac에서 git으로 읽기만), `write_deliverable`, `finish` | 2e의 작업 공간 도구 |
| 결과 | 결과물(텍스트, 6만 자까지). Task Board와 앱의 Task 목록에 남는다 | 작업 공간의 커밋. 끝나면 결과 검토 |
| 준비 | 없음. 곧바로 시작 | 첫 VM Task가 시작될 때 VM을 켜고 작업 공간을 만든다 |

- 텍스트 작업은 VM 작업 공간이 시작할 상태와 같은 것(커밋된 파일)만 본다. 경로는 저장소 안으로 제한하고 바이너리 파일은 읽지 않는다. 셸·인터넷·파일 쓰기는 없다.
- Task의 결과물은 그 Task에 의존하는 Task의 Manager(4천 자까지)와 Worker(지시서 뒤에, 2만 자까지)에게 넘어간다. 그래서 텍스트 작업으로 초안을 쓰고 VM Task가 파일로 저장하는 식으로 나눌 수 있다.
- VM Task가 하나도 없는 요청은 VM을 켜지 않고, 끝나도 결과 검토가 없다. Main의 최종 보고는 결과물을 Task 목록에서 보라고 안내한다.
- 이미 결과 검토를 기다리는 변경이 있어도 VM Task가 남지 않은 프로젝트는 시작할 수 있다.

### Task Board

CONCEPT의 Task Board를 요청(Project) 단위로 둔다. `.nidus/local/board/<프로젝트>.json`.

- Project: 지시, 상태(`planning`, `waiting_user`, `running`, `reviewing`, `done`, `stopped`, `failed`), 요약, 로드맵, 팀, Task, 질문과 답, Main의 계획 대화, 최종 보고, 작업 공간 이름.
- Task: 팀, 제목, 실행 장소, **Completion Contract**(Goal, Scope, Constraints, Acceptance Criteria, Verification), 의존 Task, 상태(`pending`, `in_progress`, `review`, `done`, `blocked`, `skipped`), 난이도, 지시서, 시도 수, 검토 기록, **Result**(요약, 검증 방법), 결과물(책상).
- 계획은 검사한다: 팀이 있는지, id가 겹치지 않는지, 의존 Task가 있는지, 의존성에 순환이 없는지, 완료 조건이 하나 이상인지.

### 실행

- 첫 VM Task가 시작될 때 VM을 켜고(꺼져 있으면) Vault의 커밋된 상태로 작업 공간을 하나 만든다. 모든 VM Task가 그 작업 공간에서 이어서 일한다.
- 준비된 Task(의존 Task가 모두 완료)를 계획 순서대로 최대 3개까지 함께 시작한다. Task마다 Manager 호출과 Worker 대화가 따로라 맥락이 섞이지 않는다. 하나가 끝나면 다음 준비된 Task를 바로 시작한다.
- **VM 차례**: VM Task의 Worker는 VM(작업 공간·브라우저)을 하나씩 쓴다. 기다리는 동안 다른 Task의 Manager 지시·검토와 VM 없는 Task는 계속 진행된다. 차례를 기다리면 진행 기록에 나온다.
- **Task별 변경**: 여러 Task가 같은 작업 공간에 커밋하므로, Worker가 VM을 놓을 때 남은 변경을 그 Task 이름으로 커밋하고 시도마다 [시작, 끝] 커밋을 기록한다. Manager는 그 Task의 커밋과 diff만 본다.
- Manager의 답을 끝내 읽지 못하는 등 실행이 실패하면 다른 Task도 멈추고, 진행 중이던 Task는 처음부터 다시 하게 표시한다. Task Board 저장은 순서대로 해서 늦게 끝난 저장이 최신 상태를 덮지 않는다.
- Task마다 새 Worker 대화로 시작한다. Manager의 검토 근거는 Worker의 요약, 도구 호출 기록(최근 40개)과 함께, VM Task는 그 Task가 만든 커밋·파일 증감·diff(마지막 시도 12KB, 이전 시도는 앞부분), 텍스트 작업 Task는 결과물(1만 5천 자까지)이다.
- 수정 요청은 같은 Worker 대화에 이어서 준다. Worker가 중간에 멈췄거나 실패했으면 새 대화로, 작업 공간에 남은 것을 확인하고 이어 가라고 준다.
- 한 Task는 최대 3번 시도한다(처음 + 수정 2번). 그래도 통과하지 못하면 진행 불가(`blocked`)다. 진행 불가 Task에 의존하는 Task는 건너뛴다(`skipped`).
- 모든 Task가 끝나면 Main이 최종 보고를 쓰고, 작업 공간이 있으면 그 변경이 결과 검토로 올라온다(2d와 같다).
- 중지하면 진행 중이던 Task는 처음부터 다시 하게 표시되고, "이어서 진행"으로 남은 Task부터 계속한다. 앱을 다시 켜도 이어 갈 수 있다.

### 앱

작업 탭의 지시 칸에서 받는 쪽을 고른다: **Main에게**(기본) 또는 **Worker에게**(2e의 단일 Worker). Main에게 지시하면 프로젝트 패널이 나온다: 계획 요약, 로드맵, VM이 필요한지, 팀별 Task(실행 장소 표시, 펼치면 Completion Contract, 결과, 검토 의견, 텍스트 작업 결과물과 복사), Main의 질문과 답 칸, 덧붙일 말, "답변 보내기"·"계획 승인하고 시작"·"중지"·"이어서 진행"·"닫기". 진행 기록에는 Main과 Manager의 말(계획, Worker 지시, 검토, 최종 보고)이 Worker의 도구 호출과 함께 나온다.

## 3b. 기억 — Home · Desk · Library

요청이 끝나도 남는 것을 만든다. 순서는 Home → Desk → Library(사용자 결정, 2026-11-13).

### 결정 (사용자, 2026-11-13)

| 항목 | 결정 |
|---|---|
| 순서 | Home → Desk → Library |
| 처음 팀 | 최소한의 기본 팀을 두고, 필요하면 Main이 제안해 승인된 직원을 일시적 또는 상설로 더한다 |
| Library | Vault 전체가 Library다(사용자 노트 + AI 노트). AI가 만든 문서는 전용 폴더에 모은다 |
| Library 쓰기 | 전용 폴더에는 승인 없이 바로 쓴다 |

### 3b-1. Home과 상설 팀

- **저장**: `.nidus/office/staff.json`(Git 추적, Vault와 함께 옮겨진다)에 Group과 Employee. Employee는 id, 이름, 소속 Group, 종류(manager/worker), Role, 사용자가 준 원칙. 모델은 적지 않는다(모델 배정은 Gateway). 파일이 없으면 기본 팀을 만든다: 조사(조사 팀장, 리서처) · 개발(개발 팀장, 개발자) · 문서(문서 팀장, 작가). Group당 Manager는 한 명이다. 사용자가 파일을 고쳐 이름·원칙·직원을 바꿀 수 있다.
- **계획**: Main은 상설 팀 목록을 받고, 맞는 팀은 id로 고른다. 맞는 팀이 없을 때만 새 팀을, 팀에 없는 Role이 필요할 때만 새 Worker(`hires`)를 제안한다. 제안마다 `keep`: `temporary`(이번 요청만, 기본) 또는 `permanent`(상설). Task에는 담당 Worker(`assignee`)가 붙는다. 새 팀에 Manager나 Worker가 빠져 있으면 채운다. 일시적인 팀의 직원은 상설이 될 수 없다.
- **승인**: 계획을 승인하면 제안도 승인된다. 상설 제안은 그때 `staff.json`에 더해지고, 일시 제안은 그 프로젝트에만 남는다. 앱의 프로젝트 패널이 제안을 따로 보여 준다.
- **정체성**: Manager와 Worker의 시스템 프롬프트는 "누구인지"(이름, id, Role, 팀, 사용자가 준 원칙, 어떤 모델이 돌리든 같은 정체성)로 시작하고 역할 정의가 뒤따른다. Manager는 지시서를 쓸 때 담당 Worker와 그 원칙을 안다.
- **State**: `.nidus/local/home/<직원>.json`에 지금 프로젝트·Task와 상태(시작/진행/검토/완료). 맥락 자체가 아니라 복구용 위치다(맥락은 Desk).
- 확인(실제 모델): "소개 문구를 쓰고 일본어로 번역" → Main이 상설 문서팀을 골랐고(번역가를 새로 뽑지 않음), "문서 팀장 → 작가"로 지시·검토가 진행됐다. 상태 파일이 직원별로 남았다.

### 3b-2. Desk와 맥락 복구

- **저장**: `.nidus/local/desk/<프로젝트>/<Task>.json`. Worker의 작업 맥락: 진행 상황, 알아낸 것, 다음 행동, 참조(경로·URL·커밋), 그리고 이전 상태의 기록(체크포인트 10개까지). 저장할 때 직전 파일을 `.previous`로 남기고, 파일이 깨지면 그것으로 복구한다. Task 상태·검토·파일처럼 다른 곳에 원본이 있는 것은 Desk에 베끼지 않는다.
- **도구**: Office의 Worker(텍스트 작업·VM 모두)는 `desk_update`를 갖는다. 시스템 프롬프트가 단계가 끝나거나 뒤에 필요한 것을 알게 되면 기록하라고 안내한다. 기록은 앱의 진행 기록에 "Desk 기록"으로 나온다. Manager는 검토 근거에서 Worker의 Desk를 본다.
- **대화 압축과의 연결**: 앞부분을 요약할 때 요약을 Desk의 체크포인트로 남기고, 요약 뒤 대화 머리에 Desk 내용을 다시 넣는다(CONCEPT의 "Session 종료 전 Desk Final Checkpoint → Context Recovery"에 해당).
- **맥락 복구**: Desk가 있는 Task를 새 대화로 시작할 때(앱 재시작, 중지 뒤 이어서 진행, 시도가 중간에 끊김) 지시 앞에 복구 안내를 붙인다. Home은 시스템 프롬프트의 정체성, Task Board는 그 순간 읽은 상태(시도 수, 검토 기록), 그리고 Desk. Desk와 Task Board·파일이 다르면 Task Board와 파일을 믿고 Desk를 고치라고 한다.
- **초안**: 텍스트 작업의 결과물은 쓸 때마다 `<Task>.draft.md`로 남겨, 재시작해도 이어 쓴다.
- Task가 통과하거나 진행 불가가 되면 마지막 체크포인트를 남기고 Desk를 닫는다.
- 확인(실제 모델): 다섯 단락 글쓰기 Task에서 Worker가 단락마다 Desk에 기록했다. 2단락 뒤 중지하고 서비스를 껐다 켜서 이어서 진행하자, Worker는 "1·2단락 완료, 다음은 3단락"이라는 Desk를 받고 3단락부터 이어 갔다. 이때 메모리에만 있던 결과물 초안이 사라진 것을 발견해 초안 저장을 넣었다. 재개 직후 Manager 모델이 2시간 가까이 막혔다(gemini 429, nemotron 시간 초과): 무료 모델 환경의 한계다.

### 3b-3. Library와 지식 고리

- **Library는 Vault 자체다**: 사용자의 노트와 AI의 노트를 함께 본다. 읽기는 지금 Vault에 있는 그대로(커밋하지 않은 새 노트 포함, `.gitignore`가 뺀 파일과 `.nidus`·`.git`·`.obsidian` 같은 숨김 폴더는 제외). 텍스트 작업의 `read_file`이 커밋된 상태만 보는 것과 다르다.
- **AI의 폴더**: AI가 쓴 문서는 Vault의 `Nidus/`에 모은다(`.nidus/office/library.json`의 `folder`로 바꿀 수 있다). 여기에는 승인 없이 바로 쓴다. 이 폴더 밖과 사용자 문서는 쓰지 않는다. 같은 이름이 있으면 번호를 붙여 덮어쓰지 않는다. 폴더가 Vault 밖을 가리키는 링크이면 아무것도 만들지 않고 거부한다. Nidus가 커밋하지는 않는다(사용자의 Git 이력은 사용자가 정한다).
- **프로젝트가 끝나면**(Knowledge Integration): 최종 보고 뒤 Main이 프로젝트를 지식으로 정리한다: 제목, 결과, 잘된 것, 잘 안된 것, 결정(3개까지), 교훈(3개까지). "오래, 또는 다시 필요한 것만" 남기라고 한다. 쓰는 문서:
  - `Nidus/Projects/<날짜> <제목>.md`: 요청, 결과, 잘된 것·안된 것, 결정·교훈으로의 `[[링크]]`, Task 요약, 텍스트 작업의 결과물 전문, 최종 보고
  - `Nidus/Decisions/<제목>.md`, `Nidus/Lessons/<제목>.md`: 각각 한 문서, 출처 프로젝트로 `[[링크]]`
  - 정리에 실패해도 프로젝트는 완료된다(진행 기록에 알린다).
- **다음 계획 때**: Main의 계획 요청에 Library 요약(최근 교훈 20, 결정 12, 프로젝트 8개의 제목·경로·첫 부분, 6천 자까지)이 붙는다.
- **Worker**: Office의 Worker는 `library_search`(단어가 더 많이 맞는 문서부터, 파일 이름도 본다)와 `library_read`를 갖는다. 시스템 프롬프트가 "사용자나 팀이 이미 써 둔 것이 있을 만하면 먼저 찾아보라"고 안내한다. Library 문서는 데이터로 표시한다.
- 확인(실제 모델): (1) "태그 규칙을 다섯 줄로" → Worker가 먼저 Library를 검색했고(없음), 끝난 뒤 Main이 프로젝트 문서 1개와 교훈 2개를 `Nidus/`에 남겼다(60초). (2) 이어서 "전에 정리한 태그 규칙과 어울리는 폴더 규칙" → Worker가 `library_search "태그 규칙"`으로 앞 프로젝트 문서를 찾아 읽고 그 규칙에 맞춰 썼다.
  (3) "태그 규칙을 Library에서 찾아 검사 스크립트 check_tags.py를 만들고 실행" → 조사팀(텍스트 작업: Library에서 규칙 추출) → 개발팀(VM: 스크립트 작성·실행) 순서로 3개 Task가 진행됐다. VM의 Worker도 Desk에 기록했고, 결과는 브랜치가 됐으며, 결정 2개와 교훈 2개가 Library에 남았다(3분 48초).
- 알려진 한계: 작은 요청에서는 교훈이 사소해지기 쉽다("파일 저장 생략" 같은 결정이 남았다). 쌓인 지식을 고르고 합치는 일은 Dream Sequence(3d)가 한다. 사용자 문서의 분류와 `[[Wiki Link]]` 연결도 아직이다.

## 3c. 앱: Main과 대화 (2026-11-13)

사용자 요청: "시험 호출" 탭을 없애고 Main과 직접 이야기하는 창을 만든다. 작업 탭의 "Main에게/Worker에게" 선택은 없앤다.

### Main 탭

- 사용자가 말하면 Main이 답한다(`src/office/chat.ts`). 질문·의논·팀과 프로젝트와 Library에 관한 것은 Main이 바로 답하고, 일을 맡기면 Main이 프로젝트를 시작한다(완결된 지시를 만들어 3a의 계획 → 승인 → 실행 흐름으로 넘긴다). 답은 `{"reply", "project"}` JSON으로 받되, JSON이 아니면 그 글을 답으로 본다.
- 메시지마다 지금 상황을 함께 준다: 열린 프로젝트(상태, 계획, Task), 검토 대기, 상설 팀, Library 요약, VM 상태. 최근 24개 메시지를 보낸다. 실패한 답은 다음 요청에서 뺀다.
- 프로젝트는 한 번에 하나다. 열린 프로젝트가 있거나 작업 중이거나 검토를 기다리는 결과가 있으면 새 프로젝트를 시작하지 않고 그 이유를 답에 붙인다.
- 대화는 `.nidus/local/main-chat.json`에 남는다(200개까지). 화면: 대화, 입력 칸, 그리고 계획 패널(질문에 답하기, 덧붙일 말, 계획 승인). Main의 답과 최종 보고는 마크다운 서식(제목, 목록, 굵게, 코드)으로 보인다.
- 작업 탭은 지켜보는 곳이 됐다: 브라우저, 네트워크 승인, 진행 기록, 결과 검토, 중지. 지시 칸과 Main/Worker 선택은 없앴다(단일 Worker에게 직접 지시하는 엔진 명령 `run`은 남아 있으나 앱에서 쓰지 않는다). "시험 호출" 탭도 없앴다.
- 확인(실제 모델): "우리 팀 구성과 지난 프로젝트에서 배운 것" → Main이 상설 팀 표와 Library의 교훈·결정을 바로 답함. "README를 읽고 한 줄 소개" → 프로젝트 시작(지시에 관련 교훈을 담음). 프로젝트가 열린 채 "다른 일도 시작해 줘" → 시작하지 않고 선택지를 물음.

### 프로젝트가 끝나면 Main이 대화에서 답한다 (2026-11-16)

- 사용자 요구: 팀의 최종 보고를 그대로 옮기지 말고, Main이 판단해 **사용자의 질문에 걸맞은 답**을 대화에 내놓을 것.
- 구현: 최종 보고 이벤트(`final`)가 오면 `MainChat.conclude()`가 대화 창(최근 24턴)에 "프로젝트가 끝났다"는 사용자 턴(사용자가 말한 것이 아님을 표시)을 덧붙여 Main에게 보낸다. 그 턴에는 `concludeBrief(project)` — 요청, 계획, Task별 상태·검토 결과·**텍스트 산출물 자체**(Task당 2만 자, 전체 6만 자까지), 팀 보고 — 가 들어가고, "찾은 내용·결과·산출물의 내용을 직접 말하고, 다른 곳을 보라고 하지 말며, 못 한 것은 그대로 말하라"고 지시한다. 답은 보통 Main 말풍선처럼 모델 표시와 제외 링크가 붙는다. 대화가 진행 중이면 끝날 때까지(최대 2분) 기다리고, Main이 답을 만들지 못하면 팀 보고를 "그대로 전합니다"라고 밝히고 붙인다. 실패·중지한 프로젝트는 한 줄로 알린다.
- 팀의 최종 보고 자체(`finalRequest`)는 작업 탭과 Library 기록용으로 그대로 남는다. 보고는 산출물을 가리키기만 하고, 대화의 답이 내용을 담는다.

### Library 탭: 읽기 전용 뷰어 (2026-11-13 제거 → 2026-11-16 복원)

앱의 Library 탭(파일 트리, 마크다운 미리보기·편집, HTML 뷰어)을 2026-11-13에 없앴다가(문서는 Obsidian에서) **읽기 전용으로 되살렸다**(사용자 결정, 2026-11-16): Main의 답이 결과물이 담긴 파일로 가는 링크를 주고, 누르면 앱 안에서 바로 읽을 수 있어야 해서다. 고치기는 여전히 Obsidian(도구 막대의 연필 → `obsidian://open`, 없으면 기본 앱).

- 보기: Markdown은 `MarkdownHTML`(헤딩·목록·표·코드·인용·`[[위키 링크]]`·이미지 embed; 노트 안의 raw HTML은 글자로만)로 렌더해 `WKWebView`에, HTML 파일은 파일 그대로 보여 준다. 스크립트와 네트워크 로드는 기본 차단("스크립트 허용"을 켠 HTML만 예외). 위키 링크·상대 링크는 뷰어 안에서 따라가고, 웹 링크는 브라우저로.
- 링크 규약: `nidus://library/<Vault 상대 경로, 공백은 %20>`. 앱의 `openURL` 환경이 이 주소를 가로채 Library 탭으로 바꾸고 그 파일을 연다(`VaultStore.libraryRequest`). `.md`는 생략해도 된다.
- Main의 답: 프로젝트 결론(`MainChat.conclude`)은 Library 기록이 끝난 뒤에 만들고, `concludeBrief`에 "Library에 쓴 파일" 목록을 넣어 결과물이 든 파일을 위 규약으로 링크하게 한다(목록에 있는 경로만).
- 이름 거르기와 ⏎ 내용 검색(`librarySearch`)은 그대로.

## 3d. Dream Sequence — Library 정리 (2026-11-14)

프로젝트마다 교훈과 결정이 쌓이면 같은 말이 겹치고 사소한 것이 섞인다. Dream Sequence(`src/office/dream.ts`)는 AI 폴더의 교훈·결정을 한 번에 읽고 정리한다.

- **하는 일**: 모델 호출 한 번(Main에 배정된 모델, "Library Manager" 시스템 프롬프트)으로 정리 계획을 받는다.
  - 합침: 같은 내용의 문서 둘 이상(같은 종류끼리)을 한 문서로. 원래 문서들의 출처 프로젝트 `[[링크]]`를 모아 붙인다.
  - 보관: 다시 읽을 가치가 낮은 문서(뻔함, 한 요청에만 해당, 뒤의 문서로 낡음).
  - 어긋남: 서로 모순되는 문서는 **고치지 않고** 사용자에게 알린다.
- **지우지 않는다**: 합친 원본과 보관한 문서는 `Nidus/Archive/<종류>/`로 옮기고 끝에 이유를 적는다. 이름으로 건 링크는 그대로 이어진다. Archive는 Library 검색과 Main에게 주는 요약에서 빠진다. 되돌리려면 원래 폴더로 옮기면 된다.
- **범위**: AI 폴더의 Lessons·Decisions만. 사용자 문서와 Projects 문서는 건드리지 않는다. 계획에 모르는 문서, 두 번 쓰인 문서, 교훈과 결정을 섞은 합침이 있으면 한 번 다시 묻고, 그래도 틀리면 아무것도 바꾸지 않는다.
- **기록**: 바뀐 것이나 어긋남이 있으면 `Nidus/Dream/<날짜> Library 정리.md`를 남긴다. 결과는 Main 대화에도 Main의 말로 올라온다.
- **언제**: (1) 사용자가 Main에게 "Library 정리해 줘"라고 하면(Main의 답에 `"tidy": true`), (2) Main 탭의 "Library 정리" 버튼, (3) 프로젝트가 끝났을 때 마지막 정리 뒤로 새 교훈·결정이 8개 이상이면 자동으로. 문서가 4개 미만이면 모델을 부르지 않는다. 프로젝트가 진행 중일 때는 시작하지 않는다.
- 확인(실제 모델, 문서 10개): 형식 제약에 관한 교훈 둘을 하나로 합쳤고, "파일 저장 생략"을 보관했고, 일부러 넣은 모순(`--fix`의 범위)을 고치지 않고 알렸다(29초).

## 3e. 사용자 문서 연결과 분류 — 제안하고, 고른 것만 적용 (2026-11-15)

AI가 사용자 문서를 고치는 유일한 곳이다. 그래서 제안만 한다(사용자 결정, 2026-11-15). `src/office/curate.ts`.

- **살펴보기**: Library의 노트(최근에 바뀐 400개까지; 숨김·무시·Archive·Dream 기록 제외)를 **전체** 읽는다(사용자 결정, 2026-11-15: 앞부분만 보는 것은 부족하다). Main에 배정된 모델, "Library Manager" 시스템 프롬프트.
  - 노트 전체가 8만 자 이하이면 모든 노트의 전문을 한 요청에 담아 바로 제안을 받는다.
  - 그보다 크면 먼저 노트를 4만 자씩 묶어 전문을 읽히고 노트마다 카드(노트 전체가 무엇을 다루는지: 주제, 요점과 결론, 이름들; 3~6문장)를 쓰게 한 뒤, 카드를 모아 제안을 받는다. 4만 자보다 긴 노트는 여러 부분으로 나눠 모두 읽고 카드를 잇는다.
  - 카드는 노트 내용의 해시와 함께 `.nidus/local/note-cards.json`에 둔다. 다음부터는 바뀐 노트만 다시 읽는다. 중간에 멈추거나 실패해도 읽은 데까지는 남는다.
- **제안 두 가지**(각 20건까지):
  - 연결: 사용자 노트 → 다른 노트(사용자 것 또는 팀의 것). 이미 연결돼 있으면 제안하지 않는다.
  - 이동: 사용자가 적어 둔 분류 규칙(`.nidus/office/library.json`의 `rules`, 평소 말로)에 따라 다른 폴더로. 규칙이 없으면 이동은 제안하지 않는다.
  - 팀 문서를 고치는 제안, 숨김 폴더나 AI 폴더로의 이동, 모르는 문서는 버린다. 모델이 문서를 id 대신 경로나 제목으로 불러도 알아듣는다.
- **적용**: 사용자가 고른 것만. 연결은 노트 끝의 `## 관련 문서` 아래에 `- [[이름]] — 이유` 한 줄을 더한다(그 절이 노트의 마지막 절이면 거기에, 아니면 새로). 노트의 나머지는 그대로다. 같은 이름의 노트가 둘이면 경로로 링크한다. 이동은 덮어쓰지 않으며, 연결을 먼저 쓰고 옮긴다. 하나가 실패해도 나머지는 적용한다. Vault 밖으로 나가는 링크 뒤의 파일이나 폴더는 건드리지 않는다. Nidus가 커밋하지는 않으므로 Git으로 되돌릴 수 있다.
- **대기**: 제안은 `.nidus/local/curation.json`에 남아 앱을 다시 켜도 기다린다. "닫기"는 적용하지 않은 제안을 버린다.
- **시작**: Main에게 "내 노트들 연결해 줘/분류해 줘"(Main의 답에 `"library": "connect"`; Library 정리는 `"library": "tidy"`), 또는 Main 탭의 "문서 연결 제안" 버튼. 제안은 대화 옆 패널에 뜨고, 분류 규칙도 그 패널에서 고친다.
- 확인(실제 모델, 노트 16개): 회의 노트 → 근거가 된 독서 노트 연결 1건, 규칙("회의록은 회의/ 폴더에")에 따른 이동 1건을 제안했고, 둘 다 적용해 노트 끝에 한 줄이 붙고 파일이 옮겨졌다(31초). 장보기 같은 무관한 노트는 제안하지 않았다.
  큰 Vault(14만 자, 노트 21개): 5번에 나눠 전부 읽고 카드를 만든 뒤 제안했다(74초). 380일치 일지의 맨 끝 결론에만 있는 관계(온실 일지 → 겨울 실험 기록)를 찾아 연결을 제안했다.
- 알려진 한계: 큰 Vault에서는 제안이 카드를 거치므로 카드에 담기지 않은 세부 관계는 놓칠 수 있다. 처음 한 번은 Vault 전체를 읽는 만큼 호출과 토큰이 든다. 400개가 넘는 Vault는 최근 것만 본다. 이동하면 경로로 건 링크(`[[폴더/이름]]`)는 고쳐 주지 않는다.
