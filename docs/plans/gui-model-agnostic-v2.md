# 모델 선택을 감추는 AI 협업 GUI 설계 계획

## 목적

사용자는 모델이나 작업자 구성을 고르지 않고, 원하는 결과를 자연어로 한 번 요청한다. 사용자와 대화하는 사장 AI가 요청을 이해하고 필요한 역할과 작업을 구성하며, 시스템은 실제 실행 가능한 모델을 정책·예산·능력에 따라 배정한다. GUI는 각 AI가 실제로 수행한 일과 결과의 근거를 보여준다.

핵심 약속은 “모델 설정 대신 결과 요청에 집중하고, 진행 상황은 실제 기록으로 확인한다”이다. 사장 AI가 직접 처리하기 적합한 간단한 요청은 단일 응답으로 끝낼 수 있다. 여러 작업이 필요한 복합 요청은 분해·실행·검토 과정을 실제로 거친다. 화면에 보이는 AI 수나 동시 실행은 로그와 일치해야 하며, 시각 효과를 위해 협업을 연출하지 않는다.

이 문서는 GUI v2의 제품·기술 설계 계획이다. 현재 동작을 v2로 오인하지 않도록 현행 제약, 단계별 구현, 완료 기준을 명시한다.

## 현행 GUI에서 확인된 간극

자연어 Plan 구성 Slice에서 사용자가 모델 정책 JSON이나 Source 경로를 직접 입력하던 간극을 줄였다. 현재 화면은 요청을 받아 로컬 Vault 자료와 ready/검증 완료된 Connection 모델을 추천하며, 사용자가 검토한 다음 Plan을 생성한다. 구성 추천은 외부 AI 호출 없이 수행된다. 복수 모델의 역할별 배정, 예산 기반 자동 선택, 연속 대화, 백그라운드 스케줄러와 자동 실행은 여전히 구현되지 않았다. 현 구현의 Source of Truth는 `DESIGN.md`, `nidus/gui.py`, `nidus/application.py`, `nidus/plan_setup.py`, `nidus/planning.py`다.

현 Gateway는 여러 호환 경로를 정책으로 호출할 수 있지만, 현재 GUI에는 연결 설정과 모델 후보 탐색을 위한 사용자 친화적 온보딩이 없다. 기본 경로가 준비되어 있다고 가정할 수도 없다. 따라서 “무료 모델 사용”을 보장하거나 사용자에게 모델 ID를 고르게 하는 것으로 문제를 해결할 수 없다. 무료 경로는 할당량·가용성·가격 조건이 변할 수 있으므로 선택 후보와 정책으로 다뤄야 한다.

현재 `develop`에 있는 PlanRuntime은 순차적인 Plan 조정 기반이다. 별도의 이전 조직 실험 브랜치가 있더라도 통합 코드로 간주하지 않는다. 재사용할 때는 최신 `develop`의 보안·승인·복구 경계와 함께 별도 감사를 거친다.

## 사용자 경험 원칙

1. **요청은 결과 중심이다.** 요청 작성 화면에는 모델, Provider, Route, JSON 정책이 나오지 않는다.
2. **연결은 최초 한 번 설정한다.** 제공자 자격증명·연결 상태·사용 가능 여부는 설정 영역에서 관리하고, 매 업무 요청에 반복해서 묻지 않는다.
3. **사장 AI가 구성하고 시스템이 제한한다.** 사장 AI는 작업 분해와 역할을 제안한다. 라우터는 허용된 연결, 기능, 가격, 예산, 동시성 한도 안에서만 실행을 선택한다.
4. **진행 표시는 실제 사건에 근거한다.** 대기·실행·완료·재시도·차단과 역할 간 전달은 지속 저장된 이벤트로 표시한다. 아직 순차 구현이라면 화면도 순차 진행이라고 보여준다.
5. **모델 정보는 기본 숨김, 필요할 때 투명하게 제공한다.** “실행 정보”를 펼치면 사용된 역할·모델·요청 시각·토큰/비용 추정·실패와 대체 경로를 확인할 수 있다.
6. **사용자 개입은 업무 판단에 한정한다.** 매번 모델을 고르는 대신, 자료 접근·예산 초과·품질 판단·불명확한 요구 등 결과에 영향을 주는 선택만 요청한다.
7. **민감 자료는 명시된 범위만 전송한다.** 사장 AI나 작업자가 전체 Vault를 임의로 전송하지 않는다. 기존 전송 승인·해시 스냅샷 경계를 유지한다.

## 제안 화면과 기본 흐름

### 1. 첫 연결

간단 설정은 호환 라우터 endpoint 하나와 그 자격증명 하나를 등록해 시작하게 한다. OmniRoute는 지원할 수 있는 연결 유형 중 하나이지 필수 종속성은 아니다. 고급 설정에서는 필요한 경우 여러 Provider 자격증명을 직접 추가할 수 있다. 둘 다 사용자는 공급자 연결만 설정하고 작업마다 모델을 선택하지 않는다.

연결을 등록하면 시스템이 모델 후보와 기능을 탐색·검증해 사장 AI 호출이 가능한지 확인한다. 기능, JSON 출력 지원, 문맥 크기, 요금 정보, 할당량/무료 상태, 지연, 최근 성공 여부를 가능한 범위에서 기록한다. 가격이나 무료 상태를 확인할 수 없으면 이를 사실처럼 단정하지 않고 불명으로 표시한다. 연결이 하나도 없으면 사장 AI가 스스로 연결을 선택할 수 없으므로, 온보딩 단계에서 적어도 하나의 사장 AI 경로를 설정해야 한다.

자격증명은 OS 자격증명 저장소(Keychain, Secret Service, Windows Credential Manager 등) 또는 검증된 비밀 관리 계층에 둔다. SQLite, Vault, 프롬프트, Git, 오류 로그에는 저장하지 않는다. GUI에서는 값 전체를 다시 읽어 보여주지 않고, 교체·삭제만 허용한다. 기존 환경변수 방식과의 호환은 유지하되 GUI가 비밀을 일반 설정 JSON에 복사하지 않도록 한다. OS별 저장 방식을 구현하기 전에 지원 플랫폼과 의존성을 확정한다.

### 2. 요청함

첫 화면은 한 개의 큰 입력란, 선택 자료 추가, 결과 형식/완료 조건(선택), 실행 예산 기본값을 제공한다. 고급 예산을 직접 변경할 수 있어도 모델명이나 Provider는 노출하지 않는다. 요청 제출 직전에는 전송될 자료 범위와 예산 한도를 사람이 이해할 수 있는 문장으로 요약한다.

사장 AI는 먼저 간단 요청인지 복합 작업인지 판별한다. 간단한 질문은 직접 답할 수 있다. 복합 요청은 목표·완료 조건·Task·의존 관계·검토 단계를 포함한 실행 계획을 만들고, 사용자에게 요약과 중요한 모호점만 보여준다. 일상적 요청은 계획을 승인하기 위한 추가 클릭 없이 진행하는 것이 기본 목표다. 데이터 접근이나 예산 정책이 실제로 요구하는 경우에만 승인을 요청한다.

### 3. 작업실

요청별 작업실은 다음을 보여준다.

- 사장 AI가 정리한 목표와 현재 단계
- 역할별 작업 카드: 예를 들어 조사, 초안, 검증, 최종 편집
- 각 카드의 실제 상태, 진행 중인 작업, 입력/출력 연결과 전달 시각
- 독립 Task와 의존 Task의 관계, 병렬 실행 여부
- 생성된 결과물, 인용/원본 참조, 검토 결과, 질문/제약
- 멈춤 이유와 사용자가 할 수 있는 다음 행동

작업자 “AI”는 사용자에게 의미 있는 역할 이름으로 표시한다. 서로 다른 모델을 썼다는 보장이 없으면 “서로 다른 AI 모델 여러 개”라고 표시하지 않는다. 역할별 호출 기록은 기술 세부정보에서 확인한다. 런타임이 실제 병렬 처리를 지원하기 전에는 카드가 동시에 움직이는 연출을 하지 않는다.

자동 진행은 시스템이 관리하되 사용자는 일시정지·재개·취소를 할 수 있다. 서버 요청 하나를 오래 열어두는 방식은 피하고, 영속 작업 큐와 이벤트 갱신을 사용한다. 먼저 폴링 방식으로 신뢰성 있는 상태 동기화를 만들고, 필요성이 확인되면 SSE를 추가한다. 재시작 후에도 중복 호출을 최소화하며 저장된 계획·승인·완료 결과로 복구한다.

### 4. 결과와 실행 정보

최종 화면은 사장 AI가 종합한 결과, 검증 상태, 근거 링크/파일, 알려진 한계와 남은 질문을 보여준다. 실제로 확인된 사용량과 비용을 추정치·미상 값과 구분한다. “실행 정보” 패널에는 역할별 모델/Provider, 시도와 대체 경로, 사용량, 비용 정보의 출처, 실행 시각, 프롬프트/입력 스냅샷 식별자를 표시한다. 비밀은 표시하거나 감사 본문에 저장하지 않는다.

## 모델 배정과 예산 정책

모델 배정은 사용자 설정이 아니라 사장 AI 제안과 결정적 라우터 정책의 결합으로 한다.

- 사장 AI는 기본적으로 유료 경로를 우선 후보로 삼는다. 단, 단가를 확인할 수 있고 요청 예산 안에 있으며 연결 검증이 통과한 경로만 사용할 수 있다.
- 일반 Worker는 요청 특성에 맞는 무료/저비용 후보부터 탐색한다. 중요 검토나 복잡한 추론에는 더 강한 후보를 배정할 수 있다.
- 모델 카탈로그는 모델 ID를 직접 노출하기 위한 기능이 아니라 라우터 선택 근거다. 기능, 입력/출력 요율, 무료 할당량 상태, context, 구조화 출력, 가용성, 오류율, 지연시간을 저장하고 갱신 시각과 출처를 붙인다.
- 사장 AI의 추천은 실행 권한이 아니다. 라우터는 allowlist, Provider 연결 상태, 요청 예산, 가격 정보, 허용 기능, 호출/토큰/동시성 한도를 다시 검사한다.
- 가격이 불명인 유료 경로는 예산 보장 상태에서 자동 실행하지 않는다. 사용자 정책이 허용하지 않는 한 차단 또는 사용자 판단으로 넘긴다.
- 재시도 가능한 인증 외 오류(일시적 네트워크, 429, 5xx 등)는 허용된 다음 경로로 제한 횟수만큼 대체할 수 있다. 인증 실패, 잘못된 요청, 검증/보안 실패는 맹목적으로 재시도하지 않는다.
- provider 호출 전에 예상 비용을 예약하고, 실제 사용량이 오면 정산한다. provider가 사용량을 제공하지 않으면 추정치/미상으로 분명히 한다. 재시작 후에도 요청 단위 누적액과 예약액이 보존되어야 한다.

초기 제품 기본 상한은 요청당 **미화 1달러 이하**를 목표로 한다. 이는 과거 사용자가 요청한 예산 한도의 초기 제품 정책으로 반영한다. 구현 전에는 실제 가격 메타데이터와 예약·환불 계산을 검증한다. 가격을 모르는 경로가 상한을 우회하지 않도록 하고, 한도 근접 시 사장 AI가 더 싼 경로로 계속할지, 멈출지, 사람에게 판단을 요청할지 정책화한다. 사용자는 상한을 낮추거나 올릴 수 있어도 모델 선택은 하지 않는다.

“무료 API”는 무료 사용량 또는 무료 요금제를 가진 후보라는 뜻이다. 무제한·영구 무료를 보장하지 않는다. 잔여 무료 할당량을 제공자에게서 확인할 수 없다면 후보의 예상 비용을 0으로 처리하지 않는다.

## 목표 아키텍처

```text
요청함 / 작업실 / 결과 뷰
        ↓
GUI API (빠른 읽기·명령, 이벤트 조회)
        ↓
사장 AI 및 Work Orchestrator
        ↓
검증된 Plan + 지속 가능한 작업 큐/스케줄러
        ↓                         ↘ 이벤트·감사 기록
모델 카탈로그 → 라우트/예산 브로커     Store
        ↓
Provider adapter (호환 라우터 또는 직접 연결)
        ↓
Worker 역할 → 결정적 검증 → 사장 AI 종합
        ↓
결과물·출처·사용량·검토 이력
```

GUI는 상태를 직접 변경하지 않고 API/Orchestrator에 명령한다. 기존 Store와 Runtime의 승인·파일 경계·복구 책임을 보존한다. 현재 PlanRuntime의 계획·DAG·완료 검증을 우선 재사용하되, 스케줄러와 모델 할당을 기존 핵심 Runtime에 섞지 않고 명시적인 서비스 경계로 둔다. 모델 호출 전후, 작업 전이, 사용자 승인, 예산 예약/정산은 지속 이벤트로 기록한다. 실패가 나도 승인되지 않은 실행을 자동으로 이어가지 않는다.

동기 HTTPServer는 GUI 응답을 빠르게 반환하도록 바꾸고, 긴 모델 호출은 백그라운드 작업으로 넘긴다. 작업 획득은 원자적이고 idempotency key를 사용한다. 프로세스 재시작 때 queued/running 상태를 정책에 따라 복구하고, 응답 수신 전 장애로 중복 과금할 수 있는 구간을 사용자에게 숨기지 않는다.

## 단계별 구현 계획

### 단계 0 — 흐름과 안전성 명세

요청함·작업실·결과 화면의 wireframe을 만들고, 간단 질의·복수 작업 조사·자료 권한 부족의 대표 시나리오를 검증한다. 요청 자동 승인 범위, 데이터 보존, 연결 자격증명 저장 방식, 원격 접속 계획을 결정한다. 현재 GUI의 실제 Browser 검증 흐름을 바탕으로 사용자에게 노출할 내부 용어를 정리한다.

### 단계 1 — 모델 비의존 요청 경험

요청 폼에서 Policy JSON과 모델 필드를 제거하고, 연결 온보딩을 추가한다. 사장 AI 부트스트랩 경로 하나를 검증하고, 요청별 금액·호출·토큰 한도를 데이터 모델과 화면에 반영한다. 단일 모델로도 동작 가능한 흐름을 먼저 완성한다. 사용자는 요청 실행 중 모델을 고르지 않아야 한다.

### 단계 2 — 영속 비동기 진행

HTTP 응답과 작업 실행을 분리한다. 작업 큐, 원자적 claim, 실행 이벤트, 재시작 복구, 일시정지/재개/취소를 구현한다. 우선 직렬 스케줄링으로 실제 진행 상태를 보여주고, UI가 화면을 새로고침하거나 서버가 재시작해도 상태가 맞는지 확인한다.

### 단계 3 — 사장 AI의 분해와 실제 역할 협업

사장 AI가 요청을 Task 그래프로 만들고, Worker·검토 역할을 실행하며, 마지막에 결과를 종합한다. 독립 Task에 한해 설정 가능한 동시성 제한 안에서 병렬 실행한다. 작업실 이벤트는 실제 모델 호출 및 역할 전달과 연결한다. 현재 PlanRuntime을 재사용하거나 확장할 때 기존 승인·품질 판단·최종 완료 조건을 우회하지 않는다.

### 단계 4 — 모델 후보 자동화와 다양한 연결

모델/Provider 탐색, 기능·가격·가용성 갱신, 연결 검증, 유료 사장 AI 경로 우선, 저비용 Worker 배정, 제한된 fallback을 구현한다. GUI는 후보를 직접 고르는 대신 연결 활성화, 요청 예산, 허용 Provider 범위만 설정하게 한다. 각 연결을 격리해서 하나의 Provider 장애가 요청 상태를 손상시키지 않는지 확인한다.

### 단계 5 — 시각적 완성도와 사용성 검증

실제 사용자 시나리오에서 요청 생성부터 결과 확인까지 테스트한다. 우선 작업실의 상태·흐름·출처를 알아보기 쉽게 다듬는다. Pixel Office나 캐릭터 연출은 이 단계 이후에, 실제 상태 모델을 정확히 투영하는 표현 계층으로만 고려한다.

## 완료 기준

- 일반 사용자가 새 요청마다 모델/Provider/Route/정책 JSON을 지정하지 않고 실행한다.
- 연결이 끊겼거나 사장 AI 후보가 없으면 적절한 연결 설정으로 안내하며, 실행된 척하지 않는다.
- 복합 시나리오에서 계획한 Task, 실제 Provider 호출, 역할 간 전달, 화면 이벤트가 서로 일치한다. 단일 경로만 호출한 경우 다중 모델 사용으로 표시하지 않는다.
- 의존 Task는 선행 결과가 완료되기 전에 실행되지 않는다. 동시 실행은 독립 Task에 한해서만 설정 상한 안에서 일어난다.
- 작업은 GUI 재접속/프로세스 재시작 후에도 복구 가능하고, 사용자가 일시정지·재개·취소할 수 있다.
- 요청별 예산 예약과 정산이 보존된다. 상한을 넘을 호출은 시작하지 않으며 미상 요금 경로도 명시 정책 없이 상한 내 실행으로 간주하지 않는다.
- 네트워크 장애·429·5xx fallback은 허용 목록과 재시도 한도 내에서만 일어난다. 인증·입력·안전 실패는 명확한 상태로 정지한다.
- 모델/Provider 연결을 끄거나 복구해도 저장된 요청·계획·결과가 손상되지 않는다.
- 자격증명이 SQLite/Vault/Git/Prompt/화면 본문/일반 로그에 나타나지 않는다. 키 교체·삭제가 테스트된다.
- 원본 접근·전송 승인과 해시 바인딩·완료 검증·사람의 품질 판단이 GUI 자동화 때문에 약화되지 않는다.
- 사용성 지표로 요청 중 모델 선택 상호작용은 0회, 요청 이후 사용자 개입 수와 사유, 첫 진행 표시 시간, 요청 완료율, 실제 비용/추정 오차, 재시도율을 측정한다.

## 범위 밖과 위험

초기 목표에 사용자의 요청별 모델 선택, 서로 다른 모델 사용 보장, 무료 무제한 이용, 검증 없이 자동 완성, 전체 Vault 자동 업로드, 공개 원격 GUI, 실제 작동 없이 움직이는 AI 사무실 연출은 포함하지 않는다. 원격 접속이 제품 목표가 되면 인증·권한·비밀 저장·네트워크 위협 모델을 별도로 설계한다.

주요 미결정 사항은 OS별 자격증명 저장 구현, GUI가 로컬 단일 사용자 앱으로 유지될지, 스케줄러 프로세스의 생명주기, 기본 예산 소진 시 정지/대체/사용자 질문 정책, 가격·무료 할당량 메타데이터의 신뢰도다. 단계 0에서 결정하고, 단계 1의 구현 범위를 고정한다.

무료 후보의 가용성과 정책은 바뀔 수 있으며, 다수 Provider API를 연결해도 모든 요청에 여러 모델이 참여하는 것은 보장되지 않는다. 모델 수보다 결과 품질·추적 가능성·예산 준수를 제품 성공 기준으로 둔다.
